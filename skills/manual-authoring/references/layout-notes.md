# 레이아웃 노트 — 당신을 물 함정들

실제 매뉴얼을 만들며 겪은 실패 모드다. 템플릿에 이미 수정이 들어 있으니, 여기서는
**왜** 그런지를 설명한다 — 되돌리지 않도록, 그리고 새 페이지가 이상하게 나올 때
막히지 않도록.

## 페이지는 고정 높이 flex 컬럼 — 내용이 소리 없이 잘릴 수 있다

각 `.page`는 정확히 A4(`height: 297mm`)이고 `display: flex; flex-direction:
column; overflow: hidden`이다. 이 고정 높이 + overflow-hidden 덕에 러닝
헤더/푸터가 고정 위치에 앉지만, **페이지 높이를 넘는 내용은 다음 장으로 넘어가지
않고 잘린다.**

여기서 서로 다른 두 가지 잘림이 나온다:

1. **이미지가 눌려서 페이지 중간에서 잘림.** flex 컬럼은 항목을 줄여서 맞춘다.
   `<img>`는 줄어드는 요소라, 페이지가 너무 길면 스크린샷을 세로로 압축하고
   `figure`의 `overflow:hidden`이 잘라낸다. 수정(템플릿): `figure { flex: none }`
   — figure는 절대 압축되지 않는다. 이걸로도 넘치면, 답은 이미지 축소가 아니라
   **내용 줄이기**다(불릿 합치기, 한 줄 빼기).

2. **페이지 하단이 잘림.** 내용이 정말로 297mm를 넘으면 맨 아래 요소(주로 주의
   박스)가 잘린다. 문구를 줄이거나 한 블록을 다음 페이지로 옮긴다.

## 폰 목업: 명시적 height로 크기를 준다, max-height 금지

flex 행 안에서 `<img>`의 `max-height`는 크기를 **확실히 제한하지 못한다** — 예상보다
크게 렌더되어 figure의 `overflow:hidden`이 하단(홈 인디케이터 / 내비 바 없어짐)을
잘라낸다. 대신 폰 행에는 **명시적 `height`**를 줘라. 그러면 너비는 비율을 따라가고
아무것도 안 잘린다.

`.row2/.row3/.row4`는 `flex: 0 0 auto`로 이미지가 줄지 않게 하고,
`justify-content: center` + 적당한 `gap`을 쓴다(`space-between` 금지 — 3장일 때
가운데가 흉하게 벌어진다).

A4 콘텐츠 폭(~170mm)에서 좌우가 안 잘리는 높이:

| 폰 수 | height | 이유 |
|-------|--------|------|
| 2 (`row2`) | 108mm | 폭 여유 많음 |
| 3 (`row3`) | 100mm | 넉넉 |
| 4 (`row4`) | **82mm** | 4×(82·0.47)+gap 이 ~170mm 아래여야 함; 더 크면 좌우 잘림 |

5장 행을 넣으면 계산: `n × (height × 비율) + (n-1)×gap ≤ 170mm`(프레임 있는 폰 비율
≈ 0.47 너비/높이). 여유를 두고 높이를 고른다.

## 데스크탑 창 캡처: 그림자 여백을 잘라내야 창이 커 보인다

세로로 긴 데스크탑 창(오버레이 앱 등)을 폰과 같은 요령으로 행에 넣을 때, **캡처를
그대로 쓰면 창이 작아 보인다.** macOS 창 캡처(Cmd+Shift+4 → Space)는 창 그림자까지
포함해서 저장되므로 실제 창은 이미지 폭의 **약 70%**밖에 안 된다. 지면에서는 이미지
높이로 크기를 정하므로, 그 30%가 고스란히 빈 여백이 된다.

`scripts/normalize_shot.py`가 창 본체 기준으로 다시 자른다(그림자는 살짝만 남기고,
잘린 단차가 안 보이도록 가장자리를 배경색으로 페이드). 같은 자리에서 창이 **1.6배쯤**
커진다. 여기에 figure의 좌우 padding·gap까지 줄이면 3장 행에서도 충분히 읽힌다.

A4 콘텐츠 폭(~170mm) 기준, 세로 창(비율 ≈ 0.69 너비/높이)이 좌우로 안 잘리는 높이:

| 창 수 | height | figure padding / gap |
|-------|--------|----------------------|
| 1 | 104mm | 5mm 3mm / — |
| 2 | 100mm | 6mm 4mm / 9mm |
| 3 | **78mm** | 5mm 2.5mm / 4mm |

실제 이미지는 `height`만 지정하고 `width: auto`로 둔다 — 둘 다 지정하면 비율이 눌린다.
자리 표시(`.ph`) 박스만 width를 함께 준다.

## 스크린샷 배경색 = figure 배경색 (안 맞으면 사각형 자국이 보인다)

이미지 배경과 figure 배경이 1~2단계만 달라도 지면에 **옅은 사각형 테두리**로 드러난다.
같은 실패를 두 경로로 겪었다:

1. 캡처 배경이 아예 다른 색(앱 미리보기의 회색 토큰 등) → 값을 맞춰 다시 캡처한다.
2. 색은 맞는데 **창 그림자가 이미지 경계에서 잘려** 가장자리만 어두운 경우 →
   여백을 넉넉히 두고 자르거나(위 스크립트) 가장자리를 배경색으로 페이드한다.

디버깅은 눈이 아니라 픽셀로 한다 — 렌더한 PNG에서 figure 패딩과 이미지 안쪽을 가로로
훑어 색이 바뀌는 지점을 찍어보면 원인이 바로 나온다. 사용자가 보낸 캡처의 색은
디스플레이 프로파일 변환으로 1~3만큼 달라질 수 있으니 **PDF 원본을 렌더해서** 재라.

## 표시(빨간 박스)는 원본을 덮어쓰지 말고 `-anno.png`로 따로

`scripts/annotate.py`로 그린다. 좌표는 이미지 크기 대비 비율(0~1)로 주므로 캡처를 다시
뽑아 해상도가 바뀌어도 그대로 쓸 수 있다. 기본값은 실제 지면에서 검증한 값이다:
선 두께 이미지 폭의 0.8%(3장 행에서 지면 0.4mm), 대상과 선 사이 여백 1.4%.
**여백 없이 딱 맞게 그리면 UI에 달라붙어 답답해 보인다.**

3장 행처럼 이미지가 많이 축소되는 자리는 지면 두께를 계산해 확인한다
(`선px / 이미지폭px × 지면폭mm`). 0.3mm 아래로 내려가면 인쇄에서 가늘다.

## 섹션은 하나의 HTML로 합친다 — PDF 병합 금지

모바일 + 콘솔(또는 여러 파트)을 한 PDF로 내려면, 모든 `<section class="page">`를
하나의 HTML로 이어 붙여 한 번에 렌더한다. **파트를 따로 렌더해 PDF를 병합하지
마라** — Quartz `CGPDFContext` 병합은 페이지 내용을 위로 밀어 러닝 헤더를 잘라낸다.
`scripts/build.py`에 이어 붙이는 패턴이 있다(공유 `<style>`, 공유 섹션 본문,
에디션별로 필요한 곳만 분기).

## 합본 폴리오는 빌드 때 연속 번호로 다시 매긴다

파트별 소스가 각자 폴리오를 하드코딩하면(앱 3~14, 콘솔 3~9, 각각 3부터 재시작),
합쳤을 때 푸터에 인쇄되는 번호가 실제 물리 쪽번호와 어긋나고 "2-6 참고(22쪽)" 같은
상호참조가 전부 틀어진다. 게다가 에디션마다 페이지 수가 달라(전용 페이지를 끼우면
그 뒤가 다 밀림) 하나의 숫자를 하드코딩할 수 없다.

해결: 합친 뒤 `scripts/build.py`의 `renumber()`로 **물리 순서대로 다시 매긴다.**
표지는 앞표지(front matter)로 세되 번호를 찍지 않고(`.folio` 없음), 내용 페이지의
`.folio`는 물리 인덱스로, 각 표지 목차의 `.pg`는 그 표지 다음부터 이어지는 번호로
채운다. 에디션마다 한 번씩 돌려 각자 맞는 번호를 얻는다. 손으로 쓴 상호참조도 이
물리 번호를 써야 푸터와 일치한다.

## 페이지 간 상호참조는 "쪽번호를 앞세운 칩"으로 — 한눈에 어디로 갈지 보이게

한 페이지가 다른 섹션을 가리킬 때(예: 데모 안내가 "환자 등록은 여기 참고"), 섹션
번호만으로는 넘겨 찾기 어렵다. 그렇다고 `웹 콘솔 2-2·2-3 (19·20쪽) / 모바일 앱
1-2·1-3 (5·6쪽)`처럼 한 줄에 몰아 쓰면 복잡해서 "어디로 가면 되지"가 안 보인다.
대신 목적지마다 **쪽번호를 앞세운 칩**으로 나눈다:

    자세히  [ 19쪽 웹 콘솔 환자 등록 ]  [ 5쪽 모바일 앱 환자 추가 ]

칩 맨 앞에 파란 쪽번호를 굵게 두면 "몇 쪽으로 가면 되는지"가 즉시 읽힌다. 파트가
여러 개면 파트 이름(앱/콘솔)을 함께 적어 구분한다(섹션 번호 1-1은 파트마다 겹침).
쪽번호는 위의 연속 폴리오와 같은 물리 번호를 쓴다. 상세 페이지가 이미 소제목으로
주제를 말하므로 칩에는 섹션 번호(2-2 등)까지 넣지 않아도 된다 — 오히려 뺄수록 깔끔.

## 문서 오프닝(전체 표지)과 파트 표지를 분리한다

여러 파트(앱 + 콘솔)를 한 권으로 낼 때, 첫 장이 한 파트의 표지("모바일 앱 사용자
매뉴얼")면 문서 전체를 대표하지 못해 어색하다. **문서 전체 오프닝 표지**(로고 +
"사용자 매뉴얼" + 부제, 목차 없음)를 맨 앞에 두고, 그다음에 각 파트 표지(제목 +
목차)를 이어라. 순서: 오프닝 → (있으면) 데모 안내 → 앱 표지·목차 → 앱 → 콘솔
표지·목차 → 콘솔.

- 오프닝은 표지이므로 `class="page cover"`(연속 폴리오에서 번호 미표시). 내용이
  적어 위로 몰리면(푸터의 `margin-top:auto` 때문) 어색하니, 오프닝만 상하·좌우
  중앙 정렬하고 푸터는 `position:absolute; bottom`으로 바닥에 고정한다. 정확한
  중앙은 살짝 낮아 보이므로 `padding-bottom`을 조금 키워 위로 당기면 시각 보정된다.
- **고객사 코-브랜드**: 데모·납품 에디션이면 오프닝에 새록 로고와 고객(병원) 로고를
  얇은 구분선으로 나란히 둔 락업이 "협업" 느낌을 준다. 로고 파일만 바꿔 에디션별로
  재사용한다.

## 퀵스타트 / 데모 안내 페이지 (선택)

데모·핸드오프용으로, 전체 흐름을 큰 번호 단계로 한 페이지에 요약하는 안내가
유용하다. **오프닝 바로 다음, 파트 표지들보다 앞**에 둔다 — 앱·콘솔을 모두 가리키는
크로스-파트 안내라 어느 한 파트의 목차 안에 끼면 어색하다. 각 단계는 한 줄짜리 쉬운
설명 + 위의 "쪽번호 앞세운 칩" 참조로 상세 페이지를 가리킨다. 보통 특정 에디션(고객·
데모)에만 들어가므로 그 에디션 빌드에서만 오프닝 뒤에 끼운다. 유치원생 수준으로 짧고
쉽게 쓰되 제품 톤(해요체 금지, 합니다체)은 지킨다.

## 항상 렌더 → 본다 → 고친다

HTML만 읽어서는 페이지가 맞는지 알 수 없다. 변경할 때마다 바뀐 페이지를 렌더하고
(`scripts/render.sh`) 실제로 본다(`scripts/verify.py` → PNG 열기). 확인: 상단 헤더
잘림, 하단 이미지 잘림, 폰 좌우 잘림, 텍스트가 푸터를 넘음. 이 루프가 곧 스킬이다 —
모든 편집마다 시간을 잡아 둔다.

## 스크린샷 교체

사용자가 페이지용 새 스크린샷을 첨부하면, 먼저 각 장을 열어 무엇인지 확인한 뒤
페이지 소제목에 맞게 배열한다(진입 → 상세 → 다이얼로그). 프로젝트의 `img/`(또는
`img-app/`)에 안정적이고 설명적인 이름으로 복사하고 `<img src>`를 갱신한다. 다시
내보내도 파일명은 그대로 두어 바이트만 바뀌고 HTML은 안 움직이게 한다. 다시 내보낸
파일은 흔한 이름(`Group 1.png`, `IMG_...2.png`)을 재사용하면서 *내용*이 바뀌므로 —
절대 이름을 믿지 말고 항상 본다.
