# 글쓰기 기준

독자는 개발자가 아니다. 영업·지원·기획처럼 사용자를 만나는 팀원과 사용자 자신이 "무엇이 바뀌었고, 나는 뭘 하면 되나"를 1분 안에 알아야 한다. 예시는 가상의 가계부 앱이다.

## 원칙

1. **사용자가 겪는 변화 단위로 묶는다.** PR 다섯 개가 한 기능이면 하이라이트 하나다. PR 하나가 사용자에게 보이지 않으면 하이라이트가 아니다.
2. **예전 → 지금으로 쓴다.** `lead`는 두 문장: 예전에는 어땠는지(불편), 이제는 어떤지(얻는 것).
3. **사실만 쓴다.** 숫자·조건·화면 문구를 쓰고, "더 편리해졌어요"·"다양한"·"강력한" 같은 평가는 뺀다. 숫자는 PR 본문·코드에서 확인한 것만 쓴다.
4. **앱 문구 그대로 쓴다.** 메뉴·버튼 이름은 `` `문구` ``로 감싸고, 경로는 `**설정 › 알림 › 반복 지출**`처럼 쓴다. `check`가 앱 소스에서 찾지 못하면 경고한다 — 지어낸 이름이다.
5. **할 일을 먼저 말한다.** `audience` 카드마다 할 일이 있는지 없는지가 첫 문장이다. 없으면 "따로 할 일이 없어요."라고 쓴다.
6. **내부 말을 쓰지 않는다.** 구현 이름(플래그·엔드포인트·스키마·내부 코드명)은 본문에서 빼고, 팀에 필요하면 `notes`로 옮긴다. 고객에게 숨기는 공급사·모델 이름은 `notes`에도 쓰지 않고 PR 링크로 가리킨다.
7. **태그 기준이다.** 이 태그에 들어간 것만 쓴다. 머지됐지만 다음 버전에 나갈 기능은 쓰지 않는다.
8. **어투 하나.** 기본은 해요체다. 제목·라벨·캡션은 명사형이나 짧은 해요체로 쓴다.

9. **실데이터로 보여 준다.** "합성 서식", "테스트 사용자" 같은 자리 채움보다, 실제 영수증·서류·기록 화면(식별 정보 가림)과 그걸로 낸 실제 결과가 훨씬 잘 읽힌다. 캡션에 무엇이 실제이고 무엇을 가렸는지 쓴다.

## 좋은 예·나쁜 예

### tagline

- ✗ `이번 업데이트에서는 다양한 기능이 추가되고 개선되었습니다.` — 아무 정보가 없다.
- ✓ `매달 나가는 돈은 한 번만 적고, 카드 명세서는 사진으로 넣어요`

### lead

- ✗ `반복 지출 기능을 추가했습니다. RecurringRule 스키마와 cron 잡을 도입했습니다.`
- ✓ `예전에는 월세·구독료를 매달 손으로 적어야 했어요. 이제 한 번 등록하면 정한 날짜에 알아서 들어가요.`

### points

- ✗ `반복 주기를 유연하게 설정할 수 있어요.`
- ✓ `주기는 매주·매월·매년 중에서 골라요. 매월은 1~28일 또는 말일로 정해요.`

### how

- ✗ `설정에서 반복 지출을 추가하면 됩니다.`
- ✓ 세 줄로 나눈다.
  1. ``**설정 › 반복 지출**에서 `추가`를 눌러요.``
  2. ``이름·금액·주기를 넣고 `저장`.``
  3. `첫 지출은 다음 날짜에 들어가요.`

### audience

- ✗ `{ "who": "기존 사용자", "what": "새로운 기능을 활용해 보세요." }`
- ✓ `{ "who": "이미 쓰던 분", "what": "**따로 할 일이 없어요.** 지난달 기록은 그대로예요. 매달 같은 지출이 있으면 반복 지출로 옮겨 두면 편해요." }`

### notes (팀 참고)

- ✓ `반복 지출은 서버 시각(한국 시간 자정)에 들어가요. 해외 사용자 문의가 오면 #418을 보세요.`
- ✓ `첨부 영상의 영수증은 실제 영수증 사진(가게 이름·카드 번호는 가림)이고, 결과는 실제 인식 결과예요. 나머지 화면은 테스트 데이터예요.`

### 캡션 (실데이터)

- ✗ `사진과 PDF를 함께 넣은 모습` — 무엇을 넣었는지 모른다.
- ✓ `실제 카드 명세서 사진 — 카드 번호·이름은 가렸어요`

### minor 카드

한두 문장, 그림은 바뀐 것이 한눈에 보일 때만.

- ✓ 제목 `'분류' 대신 '카테고리'`, 본문 ``화면 문구의 `분류`를 `카테고리`로 통일했어요. 안내 자료도 같은 말을 쓰면 좋아요.``

## 하이라이트 고르기

- 새 화면(골든 목록의 `새 화면`)이 있는 기능 → 하이라이트 1순위.
- 사용자가 거치던 절차가 바뀐 변경(줄어든 단계, 사라진 확인 창) → 화면이 같아도 하이라이트, `flow`로 보여 준다.
- 문구·아이콘·색처럼 넓지만 얕은 변화 → `minor`.
- 성능·안정성 수정 → 사용자가 체감하는 증상(“가끔 저장이 안 되던 문제”)으로 묶어 하이라이트 하나 또는 `minor`. 고친 것 목록은 변경 목록이 이미 보여 준다.
- 긴급 수정이 포함된 묶음이면 그 수정을 별도 하이라이트로 두고 `badgeTone: "safe"`로 표시한다 — 지원팀이 가장 먼저 찾는다.
