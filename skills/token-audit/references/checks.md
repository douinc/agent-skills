## C. Claude Code 체크

### C1. CLAUDE.md 크기
- [방법] 루트·중첩 CLAUDE.md 각각의 줄 수·문자 수 확인. 문자÷4로 토큰 추정.
- [기준] 공식 권장 **200줄 이하**. 200~300줄 = 개선, 300줄+ = 심각.
- [왜] CLAUDE.md는 매 세션 전문 로드되고, **커스텀 서브에이전트마다 다시 로드**된다(내장 Explore/Plan 제외). 400줄(~4K 토큰) 파일 + 서브에이전트 3회 호출 = 세션당 ~16K 토큰 고정세. 공식 문서는 "긴 파일은 준수도를 떨어뜨린다"고 하나, 1,650세션 통제 실험(arXiv:2605.10039)에서는 파일 크기의 준수도 영향이 검출되지 않았다 — 즉 **다이어트의 확실한 실익은 토큰**이고, 품질 주장은 과장하지 않는다.
- [수정안] 우선순위: ① 코드베이스에서 유도 가능한 내용 삭제(디렉토리 트리, 의존성 목록, 파일별 설명 — Claude가 직접 읽으면 됨) ② 다단계 절차 → skills 이전(C2) ③ 특정 경로에서만 필요한 규칙 → `.claude/rules/*.md`(paths frontmatter) 또는 중첩 CLAUDE.md ④ 삭제 판별 리트머스(공식): "이 줄을 지우면 Claude가 실수하는가? 아니면 지운다."

### C2. CLAUDE.md 속 절차성 콘텐츠
- [방법] CLAUDE.md에서 다단계 절차(릴리스 방법, 마이그레이션 절차, PR 프로세스, 긴 코드 예시 블록, 템플릿 전문)를 찾는다.
- [기준] 매 세션 쓰이지 않는 절차·참조 자료가 20줄+ 있으면 개선 대상.
- [왜] Skills는 시작 시 목록만 로드(컨텍스트 윈도우의 1% 예산)하고 **본문은 호출 시에만 로드** — "쓰기 전까지 거의 0토큰". "CLAUDE.md의 한 섹션이 사실(fact)이 아니라 절차(procedure)가 됐다면 스킬로 만들라"가 공식 기준. 절차를 CLAUDE.md에 두면 안 쓰는 세션에서도 매번 과금된다.
- [수정안] 해당 섹션을 `.claude/skills/<name>/SKILL.md`로 이전. 트리거가 명확하도록 description을 구체적으로 쓴다(스킬은 트리거되어야만 작동 — 설명이 약하면 지시가 조용히 누락되는 것이 이 방식의 트레이드오프임을 사용자에게 알린다).

### C3. MCP 서버 오버헤드
- [방법] `.mcp.json`(+ settings의 MCP 설정)에서 서버 목록·개수 확인. `alwaysLoad` 설정 여부 확인.
- [기준] 서버 3개+ = 사용 여부 확인 필요. 명백한 미사용 서버 = 심각. `ENABLE_TOOL_SEARCH=false` 강제 해제 = 심각.
- [왜] 실측: 서버당 10~20K 토큰, GitHub MCP 단독 26~55K, 전형적 5개 구성 ~55K 토큰이 세션 시작 전에 소모. Tool Search(기본 활성)가 이를 ~85% 줄이고 툴 선택 정확도도 **올린다**(MCP 평가에서 Opus 4 기준 49%→74% — 툴 30~50개 초과 시 정확도가 떨어지던 것의 역전). 툴 출력도 `MAX_MCP_OUTPUT_TOKENS`(기본 25K)로 상한.
- [수정안] ① 안 쓰는 서버는 `/mcp`에서 비활성화 또는 .mcp.json에서 제거(사용 여부는 사용자에게 확인) ② Tool Search 기본값 유지 ③ 매 턴 쓰는 3~5개 툴만 `alwaysLoad: true` ④ CLI로 대체 가능하면 대체(`gh`, `aws`, `sentry-cli` — 툴 정의 오버헤드 자체가 없음, 공식 권장).

### C4. 기본 모델 설정
- [방법] `.claude/settings.json`(및 settings.local.json)의 `model` 확인.
- [기준] `opus`가 기본값 = 심각(비용 관점). `sonnet` = 양호.
- [왜] 공식 문서: 예상외 과금은 대부분 "clear하지 않은 장기 세션"과 "**Opus를 기본 모델로 방치**"에서 나온다. 단가(4.5 세대 기준, 입력/출력 per MTok): Opus 4.5 $5/$25, Sonnet 4.5 $3/$15, Haiku 4.5 $1/$5 — **세대에 따라 다름**(예: Sonnet 5는 $2/$10). 리포트에는 사용자가 실제 쓰는 모델 세대의 단가를 확인해 인용한다. 품질 대가: SWE-bench Verified 기준 Opus 4.5 80.9 / Sonnet 4.5 77.2 / Haiku 4.5 73.3 — 한 단계 다운 = 약 4%p.
- [수정안] 기본 Sonnet, Opus는 아키텍처 결정·플랜 모드용(`opusplan`은 플랜 전환마다 캐시 무효화 비용이 있음을 함께 안내). 단, **모델 선택은 품질 요구가 우선** — 사용자의 작업 난이도를 물어보고 제안한다.

### C5. 서브에이전트 모델 지정
- [방법] `.claude/agents/*.md`의 frontmatter에서 `model` 필드 확인.
- [기준] 장황한 출력·정형 작업용 에이전트(테스트 실행, 로그 분석, 탐색)에 `model` 미지정(상위 모델 상속) = 개선.
- [왜] 서브에이전트는 부모 캐시를 쓰지 못하고 fresh prefix로 시작하며 CLAUDE.md도 다시 로드한다 — 에이전트는 채팅 대비 ~4배, 멀티에이전트 ~15배 토큰(Anthropic 공식). 워커를 Haiku로 지정하면 단가 1/3~1/5로 배수 비용을 상쇄. 공식 가이드: "단순 서브에이전트 작업에는 `model: haiku`".
- [수정안] 정형 워커에 `model: haiku` frontmatter 추가, 또는 전역 `CLAUDE_CODE_SUBAGENT_MODEL` 설정. 복잡한 판단이 필요한 에이전트는 그대로 둔다.

### C6. 사고(thinking)·출력 상한 설정
- [방법] settings의 `alwaysThinkingEnabled`, env의 `MAX_THINKING_TOKENS`, `BASH_MAX_OUTPUT_LENGTH`, `MAX_MCP_OUTPUT_TOKENS` 확인.
- [기준] 정보 제공 항목 — 프로젝트 성격과 함께 판단. `alwaysThinkingEnabled: true` + 루틴 작업 위주 프로젝트 = 개선.
- [왜] 사고 토큰은 **출력 요금**으로 과금되고 기본 예산이 요청당 수만 토큰일 수 있다(Opus급 30K 사고 ≈ $0.75/요청). effort 수확체감은 정량화됨: Opus 4.5 medium effort는 Sonnet 4.5 최고점과 동일 점수를 출력 토큰 76% 절감으로 달성, 쉬운 과제는 사고 256토큰에 상한 정확도 95% 도달. 루틴 작업에서 effort 낮추기는 거의 무손실, 고난도 계획에서는 유지가 맞다.
- [수정안] 루틴 위주면 effort medium 기본 + 플랜 모드만 high 제안. 대형 로그를 다루는 프로젝트면 `BASH_MAX_OUTPUT_LENGTH`(기본 30,000자) 하향 검토 — 단 너무 줄이면 에러 디테일이 잘리므로 C7(훅)이 더 나은 해법.

### C7. 훅 전처리
- [방법] settings의 `hooks` 확인. 테스트·린트·빌드가 대량 출력을 내는 프로젝트인지 package.json/Makefile 등으로 파악.
- [기준] 대량 출력 명령이 있는데 필터링 훅이 없으면 = 개선.
- [왜] 공식 패턴: PreToolUse/PostToolUse 훅으로 테스트 출력을 실패만 grep해 넘기면 "수만 토큰이 수백 토큰으로". 모델 개입 없는 결정적 처리라 품질 손실이 없다.
- [수정안] 예시 훅 제안(테스트 출력 → 실패 라인만). 적용은 사용자 확인 후.

### C8. 컴팩션 의존도
- [방법] CLAUDE.md에 compact instructions 유무, 문서화된 워크플로에서 `/compact` 상시 사용 징후 확인.
- [기준] compact instructions 있으면 양호(+). `/compact`를 상시 루틴으로 문서화 = 개선(경고).
- [왜] 요약 기반 컴팩션은 품질 손실이 실측된 유일한 절약 기법: ConstraintRot 벤치마크에서 전체 컨텍스트일 때 제약 위반 0% → **컴팩션 후 30%**(최대 59%). 반면 `/clear`는 무료·무손실, `/rewind`는 기존 캐시를 히트해 컴팩션보다 저렴. 대화에만 있는 지시는 컴팩션 후 소실된다.
- [수정안] 작업 경계 `/clear` 습관 안내, 유지해야 할 지시는 CLAUDE.md·NOTES.md로 영속화, 컴팩션은 작업 경계에서만.

### C9. 조건부 로딩 구조 활용
- [방법] `.claude/rules/*.md`(paths frontmatter), 중첩 CLAUDE.md, `.claude/skills/` 존재 확인.
- [기준] 모노레포·다영역 프로젝트인데 루트 CLAUDE.md 하나에 전부 = 개선. 구조 활용 중 = 양호(인정).
- [왜] paths 조건부 rules와 중첩 파일은 해당 경로 작업 시에만 로드 — 무관한 세션에서 0토큰.
- [수정안] 영역별 규칙을 조건부 파일로 분리.

## H. 습관 체크리스트 (모든 리포트 말미에 포함)

파일로 점검할 수 없지만 절감 효과가 가장 큰 항목들. 리포트에는 아래를 표로 요약한다.

- **H1. 캐시를 깨지 않기** — 세션 중 모델/effort 전환, MCP·플러그인 토글 금지. 캐시 읽기는 입력 정가의 10%(Anthropic 0.1x, OpenAI 90% 할인)라, 무효화 한 번이 그 세션 최대 낭비가 되기 쉽다. 100K 세션에서 "쉬운 질문만 Haiku로" 전환은 오히려 더 비쌀 수 있다.
- **H2. 작업 경계 관리** — 새 작업은 `/clear`(무료·무손실), 잘못된 탐색은 `/rewind`(캐시 히트), `/compact`는 최후 수단·작업 경계에서만(품질 손실 실측: 제약 위반 0→30%).
- **H3. 파일 통붙여넣기 금지** — "혹시 몰라서" 전체 파일 첨부 대신 에이전트가 grep으로 찾게 둔다. 근거(context rot): 관련 정보만 담은 ~300토큰 프롬프트가 113K 전체 대비 30~60%p 우세 — 컨텍스트 축소는 비용과 품질을 동시에 개선한다.
- **H4. 계측** — `/context`(무엇이 컨텍스트를 먹는지), `/usage`(스킬·MCP별 귀속), ccusage(세션·모델·캐시 히트 추적). 최적화 전후를 반드시 계측으로 검증.
- **H5. 곁다리 질문은 `/btw`** — 히스토리에 남지 않아 컨텍스트가 자라지 않는다.
- **H6. 구체적 프롬프트** — 파일 경로·검증 기준 명시가 탐색 낭비를 줄인다. 모호한 지시 자체가 토큰 비용이다.
