# GitHub 제품 UI/UX 이슈

## 개요

디자인과 실제 제품 화면의 차이, UI/UX 문제, 버그, 기능 개선 필요를 개발자가 바로 처리할 수 있는 GitHub 이슈로 정리한다. 목표는 무엇이 실제로 문제인지, 어떻게 개선되어야 하는지, 어떤 근거를 보면 되는지 짧고 분명하게 전달하는 것이다.

## 핵심 원칙

스크린샷 하네스, mock route, `capture/` 엔트리포인트, 수동 이미지 출력만 보고 실제 배포 UI가 맞다고 판단하지 않는다. 항상 아래 세 가지를 분리한다.

| 구분 | 의미 |
| --- | --- |
| 디자인 기준 | 승인된 프로토타입, 디자인 하네스, 스크린샷, 스펙, 화면 문서 |
| 실제 제품 UI | 사용자가 실제 배포 앱에서 보는 컴포넌트, 라우트, 화면 |
| 캡처 지원 코드 | mock data, capture-only 상태, 스크린샷 스크립트, 매뉴얼용 이미지 자산 |

캡처 지원 코드만 디자인과 맞고 실제 제품 UI가 다르면, 이슈는 제품 UI 차이를 기준으로 등록한다. `capture-only` 근거는 이슈 본문에 길게 넣지 말고 필요한 경우 사용자에게 별도로 보고한다.

## 새록 기준 레포 매핑

새록 이슈의 기본 GitHub 등록 대상은 `douinc/saylog`다. 단, 새록 실제 제품 소스는 `douinc/carevoice`에서 `douinc/saylog`로 이전 중이다. 마이그레이션 완료가 명시되지 않았다면 실제 배포 UI 구현은 `douinc/carevoice`를 우선 확인하고, `douinc/saylog`는 이슈 등록 대상이자 이전 대상 레포로 함께 확인한다.

| 제품 영역 | 디자인 기준 레포 | 현재 실제 구현 확인 순서 | `douinc/saylog` 이전 후보 | 기본 라벨 |
| --- | --- | --- | --- | --- |
| 앱 | `saylog-design` | `douinc/carevoice`에서 앱 구현 우선 확인 | `flutter/` | `📱 app` |
| 웹 | `saylog-console-design` | `douinc/carevoice`에서 웹 구현 우선 확인 | `web/` | `🌐 web` |
| 라이브 | `saylog-live` | `douinc/carevoice`에서 라이브 구현 우선 확인 | `saylog-live/`, `ws-gateway/` | `🎙 saylog-live` |

디자인 기준 레포, 현재 실제 구현 레포, 이슈 등록/이전 대상 레포를 분리한다. 디자인 기준 레포는 승인된 화면, 프로토타입, 캡처 기준을 찾는 곳이다. 현재 실제 구현 레포는 사용자가 지금 배포 화면으로 보는 코드의 출처다. `douinc/saylog`는 기본 이슈 등록 대상이며, 마이그레이션된 코드가 있으면 이전 대상 구현 후보로 확인한다.

`douinc/carevoice`와 `douinc/saylog` 양쪽에 코드가 있으면 어느 쪽이 현재 배포 기준인지 확인한다. 소스 이전 상태는 사용자가 이해해야 할 때 별도로 보고하되, 이슈 본문에는 기본으로 넣지 않는다. `douinc/saylog`에 코드가 있다는 이유만으로 현재 배포 UI라고 판단하지 않는다.

## 근거 첨부 방식

디자인 정합성 이슈는 디자인 기준 화면 근거를 에이전트가 우선 생성한다. 로컬에서 실행 가능한 디자인 하네스, 프로토타입, capture route, 기존 screenshot 스크립트가 있으면 Playwright/브라우저 스크린샷으로 캡처한다. 짧은 인터랙션은 Playwright video/trace 또는 기존 녹화 스크립트가 있을 때 녹화한다. 문제를 보여주는 파일이나 링크는 `문제 이미지/첨부`에, 개선 기준이나 기대 상태를 보여주는 파일이나 링크는 `개선 이미지/첨부`에 짧게 적는다. 실행 명령이나 상세 로그는 사용자가 요청하거나 실패 원인 설명이 필요할 때만 별도로 보고한다.

실제 배포 화면 근거는 접근 가능성을 먼저 판단한다. 로그인, 권한, 병원/고객 데이터, 로컬 기기 화면, 사용자의 Electron/모바일 앱 화면처럼 에이전트가 직접 볼 수 없는 화면은 사용자가 올린 스크린샷/녹화를 기준으로 정리한다. 에이전트가 접근 가능한 배포 URL이나 로컬 실행 환경이면 캡처를 시도할 수 있지만, 계정 정보나 권한이 필요하면 사용자에게 근거 업로드를 요청한다.

OS 화면 녹화나 GUI 앱 조작은 환경 권한과 사용자 승인이 있을 때만 시도한다. GitHub 도구가 파일 첨부나 업로드를 지원하면 해당 섹션에 첨부한다. 업로드를 지원하지 않으면 이슈 본문에는 문제 이미지인지 개선 이미지인지 구분해 파일명이나 링크만 적고, 업로드 상태는 이슈 본문에 쓰지 않고 사용자에게 별도로 보고한다. 업로드하지 않은 파일을 업로드했다고 쓰지 않는다.

| 근거 | 기본 생성 주체 | 처리 방식 |
| --- | --- | --- |
| 디자인 기준 화면 | 에이전트 | 디자인 하네스/프로토타입/capture route를 직접 캡처하거나 녹화하고 파일 경로를 내부 확인용으로 둔다 |
| 실제 배포 화면 | 사용자 | 사용자가 올린 스크린샷/녹화/설명을 우선 정리하고, 에이전트가 접근 가능한 환경에서만 직접 캡처 |
| 코드·라우트 근거 | 에이전트 | 실제 구현 파일, capture-only 파일, 디자인 기준 파일을 내부 확인용으로 분리한다 |

버그, UX 문제, 기능 개선 이슈는 사용자가 실제 배포 화면을 직접 보고 올린 스크린샷, 녹화, 설명을 우선 근거로 정리한다. 디자인 기준과의 비교가 핵심이 아니면 디자인 화면 캡처를 억지로 요구하지 않는다. 실제 배포 화면 근거가 부족하면 사용자에게 별도로 요청하고, 이슈 본문에는 근거 부족 상태를 쓰지 않는다.

## 빠른 이슈 등록 경로

사용자가 실제 제품 화면 스크린샷이나 녹화만 제공하고 디자인 비교를 요청하지 않았으면, 소스코드·디자인 하네스·레포 비교를 먼저 하지 않는다. 이때는 사용자가 본 화면을 기준으로 제품 영역, 환경과 제품 버전, 문제, 개선 방향만 정리해 이슈 초안을 만들거나 등록한다.

빠른 경로를 쓰는 경우:

- 사용자가 실제 앱/웹/라이브 화면을 보고 버그, UI 문제, UX 문제, 기능 개선을 말함
- 사용자가 "이슈 등록해줘", "이 화면 이상해", "이 캡처로 이슈 만들어줘"처럼 이슈화를 요청함
- 디자인 기준과 실제 구현 소스 비교가 핵심 요청이 아님

빠른 경로에서는 코드 경로와 근거는 내부 확인용으로만 둔다. 이슈 본문에는 파일 경로, 계산 과정, 소스 이전 상태, 구현 추정, 테스트 명령을 넣지 않는다. 필요한 부가 정보는 사용자에게 별도로 짧게 보고한다.

디자인 정합성 비교, 현재 구현 소스 검토, 소스 이전 상태 확인, 정책 리스크 판단을 사용자가 직접 요청했거나 제품 영역이 불명확하면 아래 전체 작업 순서를 따른다.

## 작업 순서

0. 빠른 이슈 등록 경로에 해당하는지 먼저 판단한다.
   - 해당하면 소스코드·디자인 하네스 비교를 생략하고, 사용자가 제공한 실제 화면 근거로 이슈 제목, 라벨, 본문을 작성한다.
   - 해당하지 않으면 아래 순서대로 제품 영역, 기준 화면, 실제 구현 근거를 확인한다.

1. 제품 영역과 대상 레포를 확정한다.
   - 새록 이슈면 사용자의 말, 첨부 화면, 경로를 보고 앱/웹/라이브 중 하나를 먼저 고른다.
   - 이슈 제목에 쓸 제품 영역을 정한다. 새록 이슈를 `douinc/saylog`에 등록할 때는 첫 괄호에 제품명 없이 `앱`, `웹`, `라이브`만 쓴다.
   - 다른 제품 저장소에 등록하는 이슈라면 사용자가 구분할 수 있도록 필요한 범위에서 제품명을 포함할 수 있지만, 새록 `douinc/saylog` 기본 이슈에는 제품명을 반복하지 않는다.
   - 새록 이슈이고 다른 등록 대상을 명시하지 않았으면 GitHub 등록 대상은 `douinc/saylog`다.
   - 제품 영역을 고른 뒤 `새록 기준 레포 매핑`의 디자인 기준 레포, 현재 실제 구현 확인 순서, `douinc/saylog` 이전 후보를 확인한다.
   - 소스 이전이 완료됐다는 근거가 없으면 현재 실제 구현은 `douinc/carevoice`에서 먼저 찾고, `douinc/saylog`는 이슈 등록 대상과 이전 후보로 구분한다.
   - 선택한 디자인 기준 레포에 `docs/design-harness.md`가 있으면 그 파일을 읽고, 그 안의 소스 최신화·정책·참조 문서 규칙을 따른다.
   - 제품 영역, 디자인 레포, 실제 구현 경로가 불명확하면 임의 추정하지 말고 경로 또는 레포를 물어본다.
   - 실제 제품 소스 최신화가 로컬 변경, 충돌, 인증, 네트워크 문제로 실패하면 오래된 코드로 판단하지 말고 blocker를 보고한다.

2. 문제 기준을 모은다.
   - 버그·디자인 정합성 이슈는 실제 사용자가 본 환경과 제품 버전을 확인한다. 앱/라이브는 flavor 또는 staging/production 여부, 앱 버전, build number를 우선하고, 웹은 production/staging 같은 배포 환경과 릴리스 버전, 배포 태그, 커밋, 배포 일자 중 확인 가능한 값을 쓴다.
   - 버그·디자인 정합성 이슈에서 환경과 제품 버전을 확인할 수 있으면 제목 두 번째 괄호에 함께 쓴다. 예: `[staging 2.0.1(172)]`, `[production v1.8.0]`.
   - 버그·디자인 정합성 이슈에서 제품 버전을 확인할 수 없으면 추정하지 말고, 환경만 확인되면 `[staging 제품 버전 확인 필요]`, 환경도 불명확하면 `[제품 버전 확인 필요]`를 쓴다.
   - 신규 피처와 승인된 신규 피처 디자인 핸드오프는 특정 배포 버전의 문제를 보고하는 이슈가 아니므로 환경·제품 버전을 제목에 넣지 않는다.
   - 디자인 정합성 이슈면 디자인 기준이 되는 화면, 상태, 라우트, 문서, 스크린샷을 찾고 가능한 경우 에이전트가 디자인 화면 캡처나 녹화 파일을 만든다.
   - 버그 이슈면 사용자가 올린 실제 배포 화면 캡처/녹화, 재현 경로, 실제 결과, 기대 결과, 영향받는 화면 상태를 찾는다. 에이전트가 접근 가능한 배포 URL이나 로컬 실행 환경이면 직접 캡처를 시도할 수 있다.
   - 기능 개선 이슈면 사용자가 하려는 일, 현재 막히는 지점, 기대되는 새 동작을 찾는다.
   - `needs-design` 이슈면 개발 전에 결정해야 하는 화면안, UX 원칙, 정책 해석을 찾는다.
   - 추정보다 기존 capture route, scenario 파일, screen 문서, golden image를 우선한다.
   - 근거를 대표하는 정확한 경로, URL query, state 이름, 문서 경로, 스크린샷 파일명은 내부 확인용으로 확인한다.

3. 실제 제품 근거를 모은다.
   - 사용자가 실제로 보는 제품 화면/컴포넌트 경로를 찾는다.
   - `capture/`, mock, screenshot harness 코드는 실제 화면 코드와 별도로 식별한다.
   - 가능하고 안전하면 캡처나 스크린샷으로 문제 근거를 확인한다.
   - 스크린샷 생성이 어려우면 확인 가능한 경로, 파일명, 사용자 설명을 근거로 정리하고 한계는 사용자에게 별도로 보고한다.
   - 개발 코드 수정 방법, 테스트 명령, 구현 난이도는 이슈 본문에 기본으로 넣지 않는다. 해결 방법은 개발자가 판단한다.

4. 차이와 이슈 유형을 분류한다.
   - `product-ui-mismatch`: 실제 배포 UI가 디자인 기준과 다름.
   - `capture-only-fix`: 캡처/mock 출력만 맞고 실제 제품 UI는 다름.
   - `behavior-mismatch`: 인터랙션, 상태, empty/error 처리, 플로우가 다름.
   - `policy-risk`: 구현 또는 요청이 제품 정책과 충돌할 수 있음.
   - `visual-polish`: 간격, 색, 타이포, 밀도, 아이콘, 문구, 정렬 문제.
   - `bug`: 의도한 결과와 실제 동작이 다르거나 화면 상태가 잘못 표시됨.
   - `feature`: 새 기능 또는 기존 기능 개선 제안.
   - `needs-design`: 개발 전에 디자인 또는 UX 결정이 필요함.
   - `GitHub Project Fields` 기준으로 Priority를 판단할 수 있으면 field 설정에만 사용한다. Effort는 개발자가 산정할 영역이므로 설정하지 않는다.

5. 이슈 중복을 확인한다.
   - 가능하면 GitHub connector를 먼저 사용한다.
   - connector로 부족할 때만 `gh issue list/search`를 사용한다.
   - 같은 열린 이슈가 있으면 새 이슈를 만들지 말고 기존 이슈에 코멘트하거나 업데이트한다.

6. 이슈를 등록하기 전에 최종 초안을 보여주고 확인을 받는다.
   - 사용자가 "등록해줘", "GitHub Issue 만들어줘", "create the issue"처럼 처음부터 등록을 요청해도 즉시 생성하지 않는다.
   - 등록할 저장소, 제목, 라벨, 본문 전체, 상위·하위 관계, 공유 댓글 등록 여부와 댓글 전문을 먼저 그대로 보여주고 `이 내용으로 등록할까요?`라고 확인한다.
   - 사용자가 다음 응답에서 명시적으로 승인한 뒤에만 이슈를 생성한다.
   - 사용자가 승인한 뒤 제목, 본문, 라벨, 관계, 공유 댓글이 하나라도 바뀌면 변경한 최종안을 다시 보여주고 재확인한다.
   - 직전 대화에서 동일한 최종안을 이미 확인했고 사용자가 그 안을 등록하라고 명시한 경우에는 중복 확인하지 않고 생성할 수 있다.
   - 새록 이슈는 다른 레포가 명시되지 않은 한 `douinc/saylog`에 생성한다.
   - 새록 디자인 작업 이슈의 기본 공유 대상은 `@iCodePoet @donny-son`이다. 이슈 생성 뒤 두 사람을 멘션하는 공유 댓글을 등록하되, 댓글 전문도 생성 전에 반드시 확인받는다.

## 등록 전 확인 게이트

이슈 생성은 외부 상태를 바꾸는 작업이므로 초안 작성과 등록 승인을 분리한다. 첫 등록 요청과 같은 응답에서 이슈를 만들지 않는다.

등록 전 사용자에게 아래 내용을 한 번에 보여준다.

1. 등록 저장소
2. 이슈 제목
3. 적용할 라벨
4. 이슈 본문 전체
5. 상위 이슈와 연결할 관계
6. 공유 댓글 등록 여부와 댓글 전문

사용자의 `응`, `등록해줘`, `이대로 진행해줘`처럼 현재 최종안에 대한 명시적인 승인을 받은 뒤 등록한다. 수정 요청은 승인으로 보지 않으며, 수정한 초안을 다시 제시한다.

새록 디자인 작업 이슈에는 아래 댓글을 기본안으로 제시한다. 공유 목적의 사용자를 Assignee로 지정하지 않는다. Assignee는 실제 작업 담당자에게만 사용한다.

```markdown
@iCodePoet @donny-son 디자인 변경 내역과 프로토타입 확인 부탁드립니다.
```

사용자가 댓글까지 승인하면 이슈 생성과 관계 설정이 끝난 뒤 댓글을 등록한다. 사용자가 댓글을 원하지 않거나 문구를 바꾸면 승인된 최종안만 따른다.

## 이슈 분리 기준

기본은 화면 상태 하나 또는 사용자에게 보이는 동작 하나당 이슈 하나다. 같은 화면 상태 안의 작은 시각 차이는 한 이슈로 묶는다. 아래는 별도 이슈로 분리한다.

- 정책 또는 제품 안전 리스크
- 제품 차이를 숨기는 `capture-only-fix`
- 서로 다른 화면/라우트
- loading, error, empty, active, completed 같은 서로 다른 상태
- 수정 담당이나 검증 방식이 다른 behavior mismatch
- 버그 수정과 기능 개선 제안
- 디자인 결정이 필요한 항목과 바로 구현 가능한 항목

## 디자인 하위 이슈 상태 운영

상위 기능 이슈 아래에서 디자인 작업을 관리할 때는 다음 기준을 사용한다.

- 사용자가 부모 GitHub 이슈 링크와 함께 디자인 작업을 시작하거나 UI/UX 방향·구현 방법을 요청하면, 디자인 작업 시작으로 판단한다.
- 이 경우 부모 이슈를 확인하고 같은 범위의 열린 하위 이슈가 있는지 중복 확인한 뒤, 현재 디자인 범위를 나타내는 제목만 작성한다.
- 등록 전 최종안에는 저장소, 제목, 라벨, 빈 본문, Parent issue, GitHub Project, 프로젝트 상태 `UI/UX Progress`를 명시한다. 제목만 있는 하위 이슈이므로 생성 시 공유 댓글은 등록하지 않는다.
- 사용자의 승인을 받은 뒤 하위 이슈 생성, Parent issue 연결, GitHub Project 추가, `UI/UX Progress` 설정을 순서대로 수행한다.
- 하위 이슈 생성 시에는 작업 범위가 드러나는 제목만 입력해도 된다. 본문은 비워 두고 상위 이슈 관계와 프로젝트 상태를 metadata로 설정한다.
- 작업 중에는 프로젝트 상태 `UI/UX Progress`를 사용한다. 제목이나 본문에 진행 상태를 반복해서 쓰지 않는다.
- 디자인 작업이 끝나면 최종 변경사항을 이슈 본문에 정리한 뒤 프로젝트 상태를 `UI/UX Done`으로 변경한다.
- `UI/UX Done`은 **요청된 UI/UX 디자인 작업이 완료되고 최종 변경사항이 이슈 본문에 정리된 상태**를 뜻한다.
- 개발 핸드오프 완료 여부나 개발 준비 상태는 `UI/UX Done`의 조건에 포함하지 않는다.
- 디자인 과정에서 작업 범위가 달라지지 않았다면 생성 시 입력한 제목을 그대로 유지한다.

부모 이슈 링크 없이 일반적인 디자인 작업을 시작한 경우에는 추적 이슈를 임의로 만들지 않는다. 다른 스킬이 이 절차를 호출해도 이슈 생성과 외부 상태 변경은 이 스킬의 등록 전 확인 게이트를 그대로 따른다.

## 필수 이슈 형식

이슈 초안과 GitHub 이슈 본문은 간결해야 한다. GitHub 이슈 본문을 분석 리포트처럼 만들지 말고, `## 요약`, `## 문제 기준`, `## 실제 제품 기준`, `## 수정 방향`, `## 완료 기준` 같은 많은 H2 섹션을 기본으로 쓰지 않는다. 본문은 문제와 개선만으로 개발자가 상황을 이해할 수 있게 작성하고, 이미지나 첨부는 해당 내용 바로 아래에만 붙인다.

버그·디자인 정합성 이슈 제목은 `[제품 영역][환경·제품 버전] 문제 요약` 형식으로 쓴다. 새록 이슈를 `douinc/saylog`에 등록할 때 첫 괄호에는 제품명 없이 `앱`, `웹`, `라이브`만 쓴다. 두 번째 괄호에는 사용자가 본 환경과 실제 제품 버전을 함께 쓴다. 예: `[staging 2.0.1(172)]`, `[production v1.8.0]`.

신규 피처 또는 승인된 신규 피처 디자인 핸드오프 제목은 `[제품 영역] 기능 요약` 형식으로 쓴다. 아직 배포되지 않은 기능은 특정 환경·제품 버전에 귀속되지 않으므로 `[제품 버전 확인 필요]` 같은 두 번째 괄호를 붙이지 않는다. 예: `[앱] AI 요약 다듬기 대화·음성 입력 UX 적용`.

버그·디자인 정합성 이슈에서 환경이나 버전이 일부만 확인되면 확인된 값만 쓰고 추정하지 않는다. 환경은 확인됐지만 버전을 모르면 `[staging 제품 버전 확인 필요]`처럼 쓰고, 환경도 모르면 `[제품 버전 확인 필요]`를 쓴다. 다른 저장소/다른 제품에 등록하는 이슈는 사용자가 구분해야 하는 범위에서 제품명을 포함할 수 있지만, 새록 `douinc/saylog` 이슈에는 `새록 앱`처럼 제품명을 반복하지 않는다.

디자인 정합성 이슈는 제목만 봐도 어떤 영역의 어떤 환경/버전이 현재 디자인 기준과 다른지 보여야 한다. 예: `[웹][production v1.8.0] 환자 검색 empty 상태가 현재 디자인 기준과 다름`, `[앱][staging 2.0.1(172)] 녹음 시작 CTA 문구가 현재 디자인 기준과 다름`, `[라이브][제품 버전 확인 필요] 녹음 종료 후 EMR 전송 상태가 현재 디자인 기준과 다름`.

라벨은 GitHub metadata로 설정하고, 본문에 반복하지 않는다. Priority는 설정 가능한 GitHub Project field가 있을 때만 조용히 설정하고, 이슈 본문·초안·결과 보고에는 기본 표기하지 않는다. GitHub 도구나 인증 스코프 때문에 Priority를 설정할 수 없어도 사용자가 묻지 않으면 따로 보고하지 않는다. Effort는 설정하지 않고 본문에도 추정값을 쓰지 않는다.

개발자가 코드를 어떻게 수정해야 하는지 제안하지 않는다. 사용자가 명시적으로 요청하지 않은 한 파일별 패치 방향, `AspectRatio` 같은 구현 예시, 테스트 명령, 릴리즈 방법을 본문에 넣지 않는다. 관련 화면, 컴포넌트, 코드 경로는 사용자가 요청하거나 이슈 중복 확인에 필요할 때만 사용자에게 별도로 보고한다.

기본 본문은 아래 두 섹션만 쓴다.

```markdown
문제
- [사용자가 보는 문제를 한두 문장으로 설명]
- [필요하면 사용자 영향 한 문장]

개선
- [어떻게 개선되어야 하는지]
```

문제 상황을 보여주는 이미지, 영상, 링크, 파일명이 있으면 `문제` 설명 바로 아래에만 아래 섹션을 추가한다.

```markdown
문제 이미지/첨부
- [문제 상황 이미지/영상/링크/파일명]
```

개선 기준이나 기대 상태를 보여주는 이미지, 영상, 링크, 파일명이 있으면 `개선` 설명 바로 아래에만 아래 섹션을 추가한다.

```markdown
개선 이미지/첨부
- [개선 기준 이미지/영상/링크/파일명]
```

`문제 이미지/첨부`와 `개선 이미지/첨부`는 해당 자료가 있을 때만 작성한다. 첨부가 없으면 섹션 자체를 생략하고 `첨부 없음`, `해당 없음`, placeholder를 쓰지 않는다. 일반적인 별도 `첨부/링크` 섹션은 만들지 않는다. GitHub에서 바로 볼 수 있는 URL이면 Markdown 이미지나 링크로 표시하고, 로컬 파일명만 있으면 파일명만 적고 업로드 완료로 쓰지 않는다. 부가 설명, 완료 기준, 확인 항목 섹션은 사용자가 명시적으로 요청하지 않으면 쓰지 않는다.

### 신규 피처 디자인 핸드오프 예외

승인된 신규 피처 디자인 작업을 개발 이슈로 전달할 때는 기본 `문제`·`개선` 형식 대신 아래 두 섹션만 작성한다. 새 기능은 기존 화면의 결함을 설명하기보다 무엇이 달라졌고 어디에서 검증하는지를 전달하는 것이 목적이다.

제목은 `[제품 영역] 기능 요약` 형식으로 쓰고 환경·제품 버전을 넣지 않는다.

```markdown
기존 화면 대비 변경
- [기존 진입점·입력 방식·상태 표현·확정 흐름에서 달라진 사용자 동작]

프로토타입 확인 경로
- 디자인 기준 저장소: [douinc/{design-repository}](https://github.com/douinc/{design-repository})
- 기준 커밋: [{short-sha}](https://github.com/douinc/{design-repository}/commit/{full-sha})
- 좌측 패널: `{흐름} → {그룹} → {화면}`
- 상태 선택: `{상태 칩 1}`, `{상태 칩 2}`
- 실제 진입: `{기존 화면} → {눌러야 하는 버튼·아이콘}`
```

- `기존 화면 대비 변경`은 파일별 구현 내용이 아니라 사용자가 보는 이전 동작과 변경 후 동작을 적는다.
- `프로토타입 확인 경로`에는 `localhost`만 적지 않는다. 개발자가 기준과 실행 대상을 찾을 수 있도록 제품 영역에 맞는 디자인 저장소를 GitHub 링크로 태그하고, 가능하면 기준 커밋도 링크한다.
- 앱은 `douinc/saylog-design`, 웹은 `douinc/saylog-console-design`, 라이브는 `douinc/saylog-live`를 기본 디자인 기준 저장소로 사용한다.
- 저장소 링크 다음에 좌측 패널의 흐름·그룹·화면, 프레임 밖 상태 칩, 화면 안에서 눌러야 하는 진입점을 순서대로 적는다.

### 상위·하위 이슈 관계

- 기존 상위 기능 이슈가 있고 현재 디자인 작업이 그 기능의 일부라면, 디자인 작업을 별도 이슈로 생성하고 상위 기능 이슈의 `하위 이슈(Sub-issue)`로 연결한다.
- 현재 디자인 작업 이슈의 `Parent issue`에는 기존 기능 이슈를 지정한다. 반대로 상위 기능 이슈에서는 `Add sub-issue`로 현재 디자인 작업 이슈를 추가한다.
- 현재 디자인 작업이 상위 기능 완료에 필요한 작업 단위라면 단순 `Related` 관계보다 하위 이슈를 우선한다.
- 상위 이슈 본문에 디자인 진행 내용을 덧붙이는 것으로 대체하지 않는다. 별도 하위 이슈에서 제목, 변경 내역, 프로토타입 경로와 작업 상태를 관리한다.
- 관계는 GitHub metadata로 설정하고 이슈 본문에서 부모 이슈 설명을 반복하지 않는다.

이미지가 있는 예시:

```markdown
문제
- 업데이트 온보딩 시트의 예시 이미지가 위아래로 잘려 보여서, 이미지 안에 있는 라운드 프레임의 상단/하단 보더가 보이지 않습니다.
- 1페이지와 2페이지 모두 프레임이 중간에서 잘린 것처럼 보여 화면 완성도가 떨어져 보입니다.

문제 이미지/첨부
- IMG_1694.PNG
- IMG_1695.PNG

개선
- 예시 이미지의 라운드 프레임이 위아래 보더까지 온전히 보여야 합니다.
- 화면 크기가 달라도 이미지가 위아래로 잘리지 않아야 합니다.
```

이미지가 없는 예시:

```markdown
문제
- 환자 검색 결과가 없을 때 빈 화면에 다음 행동이 보이지 않아 사용자가 무엇을 해야 할지 알기 어렵습니다.

개선
- 검색 결과가 없다는 상태와 다음에 할 수 있는 행동이 화면에서 명확하게 보여야 합니다.
```

## 이슈 유형별 구성

| 유형 | 붙이는 라벨 | 이슈에 꼭 들어갈 내용 |
| --- | --- | --- |
| 디자인 정합성 | 제품 영역 라벨 + `🐛 bug`, `🎨 ui` | 문제 설명, 문제 이미지/첨부, 개선 기준, 개선 이미지/첨부 |
| UI 버그 | 제품 영역 라벨 + `🐛 bug`, `🎨 ui` | 사용자 제공 실제 배포 화면 캡처/녹화, 재현 경로, 실제 화면 상태, 개선 후 화면 상태 |
| UX 문제 | 제품 영역 라벨 + `🧭 ux` | 사용자 제공 실제 화면 근거, 사용자가 하려는 일, 헷갈리는 지점, 문구/흐름/접근성 문제, 기대 흐름 |
| 기능 개선 | 제품 영역 라벨 + `✨ feature` | 사용자 목표, 현재 불가능하거나 불편한 점, 기대하는 방향 |
| 디자인 결정 필요 | 제품 영역 라벨 + `📏 needs-design` | 결정해야 하는 질문, 관련 정책/제약, 결정이 필요한 이유 |

하나의 이슈가 여러 유형에 걸치면 가장 먼저 해결해야 하는 성격을 기준으로 제목과 본문을 잡는다. 예를 들어 화면이 디자인과 다르고 버튼 문구도 헷갈리면 `🐛 bug`, `🎨 ui`, `🧭 ux`를 함께 붙이되, 본문에는 시각 차이와 사용자 흐름 영향을 모두 적는다.

## 라벨

`douinc/saylog`에 이슈를 등록할 때 이 스킬은 아래 8개 라벨만 사용한다. 저장소에 다른 라벨이 있어도 사용자가 명시적으로 요청하지 않으면 붙이지 않는다.

### 허용 라벨

| 분류 | 라벨 | 붙이는 경우 |
| --- | --- | --- |
| 제품 영역 | `🌐 web` | 새록 웹앱, 웹 콘솔, Teams 탭 앱 |
| 제품 영역 | `📱 app` | 새록 모바일 앱, Flutter 앱 |
| 제품 영역 | `🎙 saylog-live` | 새록 라이브 데스크톱 앱, `saylog-live/`, `ws-gateway` |
| 작업 성격 | `✨ feature` | 새 기능 또는 기존 기능 개선 제안 |
| 작업 성격 | `🐛 bug` | 의도한 대로 동작하지 않음, 실제 제품 UI/상태가 기준과 다름 |
| 디자인 축 | `🎨 ui` | 시각 표현, 레이아웃, 색, 간격, 타이포, 아이콘, 디자인 정합성 |
| 디자인 축 | `🧭 ux` | 사용 흐름, 문구, 이해도, CTA 우선순위, 접근성 |
| 디자인 축 | `📏 needs-design` | 구현 전 디자인 시안 또는 UX 결정이 먼저 필요 |

### 선택 순서

1. 제품 영역 라벨을 먼저 고른다: `🌐 web`, `📱 app`, `🎙 saylog-live`.
2. 작업 성격을 고른다: 고쳐야 할 오동작/불일치면 `🐛 bug`, 새 개선 제안이면 `✨ feature`.
3. 디자인 축을 고른다: 시각 정합성이면 `🎨 ui`, 흐름/문구/이해도/접근성이면 `🧭 ux`, 결정이 필요하면 `📏 needs-design`.

제품이 명확하지 않으면 제품 라벨을 붙이지 말고 이슈 초안에 확인 질문을 남긴다. 여러 제품에 같은 문제가 있으면 가능하면 제품별 이슈로 쪼갠다. 하나의 원인이 여러 제품에 동시에 영향을 줄 때만 여러 제품 라벨을 함께 붙인다.

### `🎨 ui`, `🧭 ux`, `📏 needs-design` 구분

| 라벨 | 붙이는 경우 | 붙이지 않는 경우 |
| --- | --- | --- |
| `🎨 ui` | 레이아웃, 간격, 색, 타이포, 아이콘, 밀도, 디자인 시안 정합성 차이 | 흐름·의미·문구 문제가 핵심이면 `🧭 ux`를 우선 |
| `🧭 ux` | 사용자가 무엇을 해야 하는지 헷갈림, CTA 우선순위가 잘못됨, 문구가 오해를 만듦, 접근성·터치 영역 문제 | 단순 픽셀/시각 정합성 문제만 있으면 `🎨 ui` |
| `📏 needs-design` | 개발자가 바로 구현하기 전에 화면안, 정책 해석, UX 결정, 디자이너 확인이 필요함 | 이미 승인된 디자인 기준이 있고 그대로 맞추면 되는 경우 |

### 자주 쓰는 조합

| 이슈 유형 | 권장 라벨 |
| --- | --- |
| 디자인 하네스 기준과 실제 제품 화면이 다름 | 제품 영역 라벨 + `🐛 bug`, `🎨 ui` |
| 캡처 전용 코드만 맞고 실제 배포 UI가 안 맞음 | 제품 영역 라벨 + `🎨 ui`, `🐛 bug` |
| 웹 화면의 레이아웃·색·컴포넌트가 디자인과 다름 | `🌐 web`, `🐛 bug`, `🎨 ui` |
| 모바일 앱 화면의 터치 영역·접근성·흐름이 어색함 | `📱 app`, `🧭 ux` |
| 새록 라이브 화면 캡처와 실제 Electron UI가 다름 | `🎙 saylog-live`, `🐛 bug`, `🎨 ui` |
| 버튼 위치나 CTA 우선순위 때문에 사용 흐름이 어색함 | 제품 영역 라벨 + `🧭 ux` |
| 문구가 기능 의미를 혼동하게 함 | 제품 영역 라벨 + `🧭 ux` |
| 구현 전 디자인 결정이 필요함 | 제품 영역 라벨 + `📏 needs-design` |
| 새 화면이나 흐름 개선 제안 | 제품 영역 라벨 + `✨ feature`, 필요 시 `📏 needs-design` |
| 실제 동작이 의도와 다르거나 UI 상태가 잘못 분기됨 | 제품 영역 라벨 + `🐛 bug` |

허용 라벨로 표현하기 어려운 성격은 사용자에게 별도로 보고하고, 라벨을 추가하지 않는다. 라벨이 저장소에 없으면 사용자가 라벨 관리를 요청하지 않은 한 새 라벨을 만들지 않는다.

## GitHub Project Fields

`douinc/saylog` 이슈를 GitHub Project에 등록하거나 Project fields를 설정할 수 있으면, 라벨과 별도로 Priority만 판단해서 field에 설정한다. Project field 옵션 이름은 저장소/프로젝트의 실제 옵션을 우선한다. 아래 표의 P0-P3는 의미 기준이며, 실제 옵션이 `Urgent`, `High`, `Medium`, `Low`처럼 다르면 가장 가까운 옵션으로 매핑한다. Priority는 이슈 본문, 초안, 최종 보고에 기본 표기하지 않는다. 옵션을 조회할 수 없거나 GitHub 도구가 fields 설정을 지원하지 않으면 조용히 건너뛰고, 사용자가 Priority 상태를 물었을 때만 설정 불가 사유를 설명한다.

| 의미 기준 | Priority 판단 |
| --- | --- |
| P0 / Urgent | 환자 안전, 개인정보, 데이터 손실, 핵심 진료·기록 흐름 차단, 배포 차단 |
| P1 / High | 주요 사용자 흐름이 깨짐, 다수 사용자가 볼 가능성이 큼, 승인된 디자인과 크게 달라 신뢰도나 업무 속도에 영향 |
| P2 / Medium | 특정 화면/상태에서 명확한 UI/UX 문제나 디자인 불일치가 있지만 우회 가능 |
| P3 / Low | 작은 시각 보정, 문구 다듬기, 낮은 빈도 상태, 다음 정기 개선에 포함 가능한 문제 |

Effort는 설정하지 않는다. 수정 난이도는 실제 구현 범위, 코드 구조, 테스트 영향, 배포 절차를 개발자가 확인해야 하므로 스킬이 산정하지 않는다. GitHub Project에서 Effort가 필수라 이슈 생성이나 등록이 막히면 값을 추정해서 넣지 말고, 사용자에게 `Effort 필드가 필수라 개발자 산정 필요`라고 보고한다.

## 출력 형식

이슈를 초안 작성할 때는 아래 순서로 답한다.

1. 이슈 제목: 버그·디자인 정합성은 `[제품 영역][환경·제품 버전] 문제 요약`, 신규 피처는 `[제품 영역] 기능 요약`
2. 라벨: 허용 라벨 중 실제로 붙일 라벨
3. 이슈 본문: 일반 이슈는 `문제`·`개선`, 승인된 신규 피처 디자인 핸드오프는 `기존 화면 대비 변경`·`프로토타입 확인 경로`
4. 관계: 상위 기능 이슈가 있으면 현재 작업을 별도 하위 이슈로 연결
5. 등록 전 확인: 저장소·제목·라벨·본문·관계를 보여주고 사용자 승인 요청
6. 상태: 생성 완료, 중복으로 생략, 사용자 확인 필요, 사용자 업로드 필요 중 현재 상태

사용자에게 보여주는 설명은 위 metadata를 포함할 수 있지만, GitHub 이슈 본문은 짧게 유지한다. 상세 코드 분석, 계산 과정, 테스트 명령, 구현 제안은 사용자가 따로 요청했거나 작업 상태 보고가 필요할 때만 이슈 밖에서 별도로 제공한다.
