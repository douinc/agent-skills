# 노트 양식과 문장 기준

## 양식

```md
<!-- tag: app-v1.4.0 -->
<!-- base: app-v1.3.2 -->
<!-- omit: #231 배포 워크플로 변경이라 사용자에게 닿지 않음 -->

이번 버전에서 가장 큰 변화 한 문장.
[화면으로 보는 쇼케이스](주소)        ← `notes link`가 넣는다. 손으로 쓰지 않는다

## 새 기능
- **기능 이름**: 무엇을 할 수 있게 됐는지. 어디서 쓰는지(**메뉴 › 경로**). (#210, #214)

## 달라진 점
- **무엇이**: 예전에는 어땠고 지금은 어떤지. (#220)

## 고친 것
- 어떤 상황에서 무엇이 잘못됐었고 지금은 어떤지. (#225)

## 올릴 때 할 일
- 사용자가 할 일은 없어요.           ← 없을 때도 구역은 둔다
- 지원 담당: ○○ 문의가 오면 ○○라고 안내해요.

## 범위
`app-v1.3.2` → `app-v1.4.0` · PR 18건(새 기능 4 · 고친 것 6 · 내부 정리 8) · [전체 비교](주소)
```

머리말 주석은 Release 본문에 함께 올라가지만 GitHub 화면에는 보이지 않는다(`audit`이 본문만으로 판정하는 데 쓴다). `base`는 `check`가 범위를 다시 계산하는 데 쓴다.

## 문장 기준

- **주어는 사용자다.** "드롭다운 컴포넌트를 교체" (X) → "번역 언어를 59개 중에서 검색해 골라요" (O)
- **달라진 점은 예전 → 지금 두 문장.** 예전 동작을 모르면 무엇이 달라졌는지 읽히지 않는다.
- **고친 것은 증상으로.** "null 처리 누락 수정" (X) → "서식이 0개일 때 설정 화면이 열리지 않던 문제를 고쳤어요" (O)
- **사실만.** 숫자·조건·화면 문구는 PR 본문과 태그 시점 소스에서 확인한 것만 쓴다. "더 빨라졌어요"는 잰 숫자가 있을 때만.
- **화면 문구는 그대로.** 버튼·메뉴 이름은 백틱이나 굵게로 앱에 적힌 대로 쓴다. 지어내지 않는다.
- **한 항목 한두 문장.** 길어지면 쇼케이스 몫이다.
- **말투는 저장소 설정을 따른다**(`tone`, 기본 해요체). 한 노트 안에서 섞지 않는다.

## 나쁜 예와 고친 예

```md
## 변경 사항
- Merge pull request #412 from org/main
- feat(editor): sync open document after history reformat (#398)
- chore: bump version to 1.4.0 (#415)
```

위 노트의 문제: 병합 줄은 아무 정보가 없고, 커밋 제목은 개발자가 한 일이며, 버전 올림은 변경이 아니다.

```md
문서를 팀원과 함께 고칠 수 있게 되고, 내보내기가 PDF까지 넓어졌어요.

## 새 기능
- **함께 편집**: **공유 › 편집 권한**으로 초대한 사람과 같은 문서를 동시에 고쳐요. 누가 어디를 고치는지 색으로 보여요. (#398, #402)

## 달라진 점
- **내보내기**: 예전에는 Markdown으로만 내보냈어요. 이제 `PDF`도 고를 수 있어요. (#407)

## 고친 것
- 표가 든 문서를 열면 스크롤이 맨 위로 튀던 문제를 고쳤어요. (#410)

## 올릴 때 할 일
- 사용자가 할 일은 없어요. 자동 업데이트로 받아요.
```

## 무엇을 빼나 (omit)

- CI·배포 워크플로, 개발 도구, 테스트만 바꾼 PR
- 다음 버전에서 켜질 기능의 보이지 않는 준비 작업 — 다만 같은 구간에 그 기능이 켜졌으면 켠 PR과 묶어 싣는다
- 뺄 때는 머리말에 `<!-- omit: #번호 이유 -->` 한 줄. 한 주석에 번호 여러 개도 된다.
