# release-notes — 읽으면 무엇이 바뀌었는지 아는 릴리스 노트

릴리스 노트가 커밋 제목 목록이면 쓰는 의미가 없다. 이 스킬은 태그 구간의 PR을 **본문까지** 읽어 사용자가 겪는 변화 단위로 묶고, 고정 양식에 맞춰 쓰고, `check`로 빠진 변경·섞인 변경·복사된 노트를 막은 뒤 GitHub Release 본문을 바꾼다. CI가 이미 릴리스를 만들었어도 본문만 바꾸므로 워크플로는 건드리지 않는다.

경로 표기: `<SKILL_DIR>`는 이 SKILL.md가 있는 폴더다. 명령은 대상 저장소 안에서 `python3 <SKILL_DIR>/scripts/notes.py …`로 실행한다(아래에서는 `notes`로 줄인다).

## 진행 체크리스트

- [ ] 0 준비 — 설정·태그 최신화
- [ ] 1 `init` — 범위와 재료
- [ ] 2 재료 읽기 — PR 본문
- [ ] 3 노트 쓰기
- [ ] 4 `check` 오류 0
- [ ] 5 `publish --dry-run`으로 올릴 본문 확인 → 사용자 확인 → `publish`
- [ ] 6 쇼케이스 넘기기 (화면이 바뀐 릴리스만)

## 0. 준비

- `git fetch --tags origin`으로 태그를 맞춘다. 작업 폴더가 원격보다 뒤처져 있으면 최신 기본 브랜치의 worktree에서 한다(설정 파일이 최신이어야 한다).
- 설정은 release-showcase와 같은 `.release-showcase/config.json`을 읽는다(`apps.<키>.tagPrefix`·`sourceDir`·`shipScopes`, `denyPattern`). 파일이 없으면 앱 하나·접두사 `v`·저장소 전체로 본다. 이 스킬만의 선택 항목은 같은 파일의 `releaseNotes`에 둔다:

```jsonc
"releaseNotes": {
  "serverDirs": ["backend/"],     // 같은 구간의 서버 변경을 재료에 싣고, 노트에서 그 PR을 인용할 수 있게 한다
  "keepSections": ["산출물"]       // CI가 쓴 본문에서 남길 구역 제목(기본값). 맨 위 key=value 빌드 정보 줄은 늘 남긴다
}
```

- 필요한 것: git, Python 3.10+, `gh`(PR 본문·Release 읽기/쓰기).
- 저장소에 CHANGELOG.md가 있고 릴리스 워크플로가 그 구역을 노트로 쓰는 저장소는 CHANGELOG 구역을 재료로 삼아 양식만 맞춘다. CHANGELOG를 대신하지 않는다.

## 1. 범위

```bash
notes init <이번 태그>              # 기준 태그를 고르고 재료와 노트 뼈대를 만든다
notes init <이번 태그> --base <태그>
```

- 기준(base)은 **바로 앞 정식 태그**다. 노트는 정식 릴리스마다 하나씩 쌓이므로 구간이 겹치지 않아야 한다. staging·beta·rc 태그는 기준이 아니다(테스트 채널 노트는 아래 따로). 정식으로 나가지 않은 중간 버전이 있으면 노트의 범위 구역에 한 줄 적는다.
- 쇼케이스는 다르다: 며칠 만에 핫픽스가 이어진 사슬은 건너뛰고 사용자가 실제로 머물던 버전을 기준으로 잡는다. 그래서 쇼케이스 하나가 노트 여러 개의 구간을 덮을 수 있다.
- 만들어지는 것: `.release-notes/<태그>.md`(노트, 커밋 대상), `.release-notes/.work/<태그>/brief.md`(재료, gitignore).

### 태그 전에 쓰기 (권장)

노트를 버전 올림 PR에 함께 싣으면 리뷰를 받고, 태그가 올라가는 순간 노트가 준비돼 있다.

```bash
notes init <다음 태그> --at <릴리스될 브랜치>    # 예: notes init app-v1.4.0 --at origin/main
```

- 기준은 지금까지의 마지막 정식 태그다. 노트 머리말에 `<!-- at: … -->`가 남아 `check`가 그 브랜치 기준으로 본다.
- 노트 파일을 버전 올림 PR에 커밋한다. PR이 병합된 뒤 태그 전까지 더 들어온 변경이 있으면, 태그 뒤 `check`가 실제 태그로 다시 계산해 빠진 PR을 알려 준다 — 그때 채우고 올린다.
- `publish`는 태그가 올라간 뒤에만 된다.

## 2. 재료

`brief.md`를 처음부터 끝까지 읽는다. 새 기능·고친 것은 PR 본문 앞부분이 실려 있다. 잘린 본문에서 사용자 동작이 안 보이면 `gh pr view <번호>`로 전체를 읽는다. **PR 제목만 보고 쓰지 않는다** — 제목은 개발자가 한 일이고, 노트는 사용자가 겪는 일이다.

## 3. 노트 쓰기

양식과 좋은·나쁜 예는 `references/writing.md`를 먼저 읽는다. 요점:

- 첫 줄: 이번 버전에서 가장 큰 변화 한 문장(120자 안쪽).
- `## 새 기능` → `## 달라진 점` → `## 고친 것` → `## 올릴 때 할 일` → `## 범위` 순서. 앞의 셋은 내용이 없으면 구역을 지운다. 뒤의 둘은 반드시 둔다.
- 항목은 PR 단위가 아니라 **변화 단위**다. 한 기능을 만든 PR 여럿은 한 항목에 묶고 번호를 모두 단다 `(#12, #15)`.
- 새 기능·수정 PR인데 사용자에게 닿지 않는 것(CI·개발 도구·보이지 않는 준비 작업)은 싣지 않고 머리말에 `<!-- omit: #번호 이유 -->`를 남긴다. 이유 없이 빼지 않는다.
- 내부 정리는 범위 구역의 건수로만 남는다(`init`이 채워 둔다).
- 올릴 때 할 일: 사용자·지원 담당·운영자가 할 일. 없으면 "할 일 없음"이라고 쓴다. PR 본문의 하위 호환·배포 순서·알려진 한계에서 찾는다.

## 4. 검사

```bash
notes check <태그>
```

- `✗` 오류: 병합 커밋 줄, `feat:` 같은 커밋 접두사, 채우지 않은 TODO, 빠진 필수 구역, **범위 안 새 기능·수정 PR 누락**, **범위 밖 PR 인용**, 직전 정식 노트와 같은 본문, 쓰지 않기로 한 말(`denyPattern`). 전부 고친다.
- `△` 경고: PR 번호 없는 항목, 긴 요약, 양식 밖 구역. 고치거나 둘 이유를 보고에 적는다.

게이트: 오류 0.

## 5. 올리기

```bash
notes publish <태그> --dry-run    # 올릴 본문을 .work/<태그>/publish-body.md에 만든다 (올리지 않음)
notes publish <태그>              # 검사 → gh release edit (Release가 없으면 원격 태그 확인 뒤 만든다)
```

- Release 본문은 팀·고객이 보는 글이다. **`--dry-run` 결과를 사용자에게 보여 주고 확인을 받은 뒤 올린다.** 사용자가 이 태그를 올리라고 이미 말했으면 바로 올린다.
- CI가 쓴 본문 중 `keepSections` 구역(기본: 산출물)과 맨 위 빌드 정보 줄은 노트 아래에 남는다. 바꾸기 전 본문은 `.work/<태그>/original-body.md`에 남으니, 되돌리려면 `gh release edit <태그> --notes-file` 로 그 파일을 올린다.
- 태그가 원격에 없으면 멈춘다. 태그를 만드는 일은 프로젝트의 릴리스 절차(브랜치 전략·워크플로)가 한다.
- 올린 뒤 `.release-notes/<태그>.md`를 저장소에 커밋한다(프로젝트 규칙대로 PR).

## 6. 쇼케이스 넘기기

화면이나 쓰는 법이 바뀐 릴리스면 release-showcase 스킬로 이어 간다. 같은 설정 파일을 쓰므로 범위가 맞는다.

- `showcase init <태그>`로 시작하고(기준은 쇼케이스 규칙으로 고른다), 노트의 **새 기능·달라진 점** 항목을 하이라이트 후보로, **고친 것**을 작은 카드 후보로, **올릴 때 할 일**을 독자별 카드 재료로 쓴다.
- 쇼케이스가 공유된 뒤 주소를 노트에 넣고 다시 올린다:

```bash
notes link <태그> <쇼케이스 주소>
notes publish <태그>
```

- 고친 것만 있는 작은 릴리스는 쇼케이스를 만들지 않는다. 노트만으로 끝낸다.

## 테스트 채널 노트

staging·내부 테스트처럼 테스터가 받는 채널의 출시 노트(프로젝트의 배포 노트 파일, 배포 알림 본문)는 정식 노트와 규칙이 다르다. `.release-notes/`에 노트를 만들지 않는다.

- **범위는 마지막 정식 릴리스 이후 누적**이다. 테스터는 정식 버전 이후 바뀐 것을 한곳에서 본다.
- **테스트 빌드 버전별 칸으로 나눈다.** 칸 머리는 `[2.2.3+199]` 한 줄이고 최신 칸이 맨 위다. 새 테스트 빌드를 내면 맨 위에 칸을 더하고 아래 칸은 그대로 둔다. 양식은 `references/writing.md`.
- 변경을 넣을 칸은 그 변경이 처음 들어간 테스트 빌드 태그다. `git merge-base --is-ancestor <변경 커밋> <테스트 태그>`가 참인 가장 오래된 태그로 정한다.
- 한 줄은 한 칸에만 쓴다. 공통 꼬리말(예: "그 밖에 여러 오류를 고쳤어요")도 칸마다 반복하지 않는다.
- 글자 수 상한이 있는 채널(예: Play 변경사항 500자)에는 맨 위 칸만 보낸다.
- 정식 릴리스로 승격하면 테스트 노트를 비우고 다음 테스트 빌드부터 새로 쌓는다. 정식 채널 노트(Release 노트·스토어 문구)는 지난 정식 릴리스 이후 전체를 사용자 관점으로 한 덩어리로 쓴다. 버전 칸은 두지 않는다.

```bash
notes check-test <노트 파일> [--limit 500]   # 칸 머리 형식·최신이 위·칸 사이 반복 줄, --limit은 맨 위 칸 글자 수
```

## 지난 릴리스 점검

```bash
notes audit --limit 30
```

이미 나간 정식 릴리스를 훑어 병합 줄·접두사 목록·복사된 본문·빠진 변경 수를 보여 준다. 다시 쓸 대상을 고를 때 쓴다. 다시 쓰는 절차는 위 1~5와 같다.

## 함정

- **서버 태그(CalVer, 하루에 여러 개)에는 노트를 쓰지 않는다.** 앱 노트의 달라진 점·올릴 때 할 일에 그 앱 사용자가 느끼는 서버 변경만 싣는다(`serverDirs`).
- **스토어 문구와 릴리스 노트는 다르다.** 스토어 문구(앱 마켓 "새로운 기능")는 최종 사용자용 서너 줄이고 프로젝트 파일이 따로 있다. 그 파일을 고치지 않고, GitHub Release 노트만 이 스킬이 쓴다.
- 같은 버전의 재빌드(빌드 번호만 오른 태그)는 직전 노트를 복사하지 않는다. 그 사이에 실제로 바뀐 것만 쓰고, 첫 줄에 재빌드 이유를 적는다.
- conventional commit을 쓰지 않는 저장소는 변경이 전부 내부 정리로 모여 누락 검사가 느슨해진다. 그럴 때는 재료의 내부 정리 목록을 직접 읽어 사용자 변경을 고른다.
- 노트에 내부 구현어(파일 이름, 함수 이름, 엔드포인트)와 `denyPattern`에 걸리는 이름을 쓰지 않는다. 화면 문구와 메뉴 경로는 앱에 적힌 그대로 쓴다.
